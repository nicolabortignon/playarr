# Decisions

Lasting decisions, oldest first, with the reason behind each. Later rows can supersede earlier ones; where that happened the earlier row says so. How things work today is in the other docs ([index](README.md)); this page is the why.

## Foundations and the web app

| Date | Decision |
|---|---|
| 2026-10-27 | Web-first React PWA with a Node/Fastify companion server, because Lidarr can't stream audio itself ([architecture](architecture.md)). |
| 2026-10-27 | The server reads audio through a pluggable `MediaSource`: `sftp` for local dev (no mounts), `local` disk when deployed next to Lidarr, `none` until configured. `/stream` only serves ids the catalog knows; the client never sends a path. |
| 2026-10-27 | Added `MEDIA_SOURCE=ssh` (exec `stat`/`tail`/`head` over SSH) because UGOS's SFTP hides shares not created in its UI. Config keys renamed `SFTP_*` → `SSH_*`. Paths are shell-quoted; channels close when the browser aborts. Limit: sshd `MaxSessions` (10) caps simultaneous streams per connection. |
| 2026-10-27 | Discover and requests: Deezer for songs, Lidarr for artists and albums, MusicBrainz for discographies and name → id resolution. Albums are resolved to MusicBrainz ids only at request time (not per search result), which keeps search fast. |
| 2026-10-27 | The dev server runs outside Claude's sandbox: the sandbox blocks some external hosts (Cover Art Archive, Lidarr's image CDN). The code degrades gracefully when the internet is flaky (songs may be missing; covers retry once). |
| 2026-10-27 | Single `<audio>` element so iOS background playback keeps working. *Superseded 2026-11-01: two elements taking turns, which iOS keeps playing in the background too; Web Audio only on desktop (2026-11-02).* |
| 2026-10-27 | Visual direction "liner notes": warm near-black, Gloock display serif, Schibsted Grotesk UI, DM Mono for specs and durations. The accent colour comes from the current cover art; there's a subtle film grain. |
| 2026-10-27 | Stack: React 19, Vite 8, Tailwind 4, React Router 7 (pinned below v8), TanStack Query 5, Zustand 5, Motion, Fastify 5, zod 4, TypeScript 7. |
| 2026-10-28 | Playlists: entries keyed by recording id plus a title/artist/album snapshot, so songs that leave the library stay visible (greyed out) instead of vanishing; duplicates allowed; order kept as integer positions rewritten on reorder. Mobile tabs: Home · Search · Library · Queue, with Library collecting playlists, favorites, artists, albums and requests. |
| 2026-10-28 | The favicon is redrawn in the accent colour of the playing track (canvas → PNG, since Safari ignores SVG favicons). |
| 2026-10-28 | Favorites are keyed by MusicBrainz **recording id**, not a Lidarr track id, so they survive re-imports and quality upgrades. Stored server-side in SQLite through Node's built-in `node:sqlite` (no native dependency). User data lives in `DATA_DIR`, separate from the deletable cache. |
| 2026-10-28 | Recommendations come from ListenBrainz (open data, no key, MusicBrainz ids end to end) rather than Last.fm (needs a key; matches by name) or Deezer radio (popularity-driven, weaker for niche music). The labs API takes one seed per call, so up to 10 calls run in parallel. |
| 2026-10-29 | Playlist covers are pinned once drawn and changed only from the picker (after comparing with Apple Music): redrawing on every change undermined recognisability. Titles are part of the cover except on thumbnails under 120 px ([playlist covers](server/playlist-covers.md)). |
| 2026-10-29 | Production build: tsup must keep the `node:` prefix (`removeNodeProtocol: false`), or `node:sqlite` becomes `sqlite` and `pnpm start` crashes. Dev (tsx) is unaffected, which hid it. |
| 2026-10-29 | Covers use curated palettes (chromotome) rather than computed ones, and gained the Currents (flow field) and Colonies (Physarum) layouts. AI image models ruled out: no GPU on the NAS, external services would receive listening data, and results aren't deterministic. |
| 2026-10-29 | Playlist covers are generated from **measured audio** (ffmpeg plus Playarr's own DSP), not metadata: Deezer's BPM is often 0, AcousticBrainz is gone, and analysis covers every song including obscure ones. Only ~5 MB of low-rate mono PCM per song crosses the network, once. |
| 2026-10-29 | Client-side caching: the page downloads whole songs into Cache Storage and the service worker serves byte ranges from them (rather than the worker caching what `<audio>` streams, which is only ever partial 206 responses). The page owns the budget and LRU, so the worker stays simple. Needs HTTPS or localhost ([web](web.md)). |
| 2026-10-31 | Speed on phones and the NAS: long grids render as you scroll, covers load a few at a time (on-screen first), rarely used pages load on first open; on the server, matches rebuild from the last scan, analysis and fingerprinting run at low priority, and a larger I/O threadpool (`UV_THREADPOOL_SIZE=16`) keeps streams from queueing behind image work. |

## Sources, catalog and settings

| Date | Decision |
|---|---|
| 2026-10-30 | One catalog in SQLite fed by source adapters (chosen over merging in-memory snapshots, and over handing folders to Lidarr). Lidarr is the first adapter and is optional. New rows take the Lidarr id when it's free, so existing links, saved queues and offline songs kept their ids with no migration ([sources and catalog](server/sources-and-catalog.md)). |
| 2026-10-30 | Folders may hold anything (music Lidarr can't know, an existing collection, an overlapping second drive, Lidarr's own folder): overlap and messy metadata are normal. One entry per song and album; albums merge by MusicBrainz release group. Manual fixes are stored in Playarr only and tags are never rewritten. Periodic scans (size + mtime) plus Rescan, no live watching. |
| 2026-10-30 | Sources live in the database. `.env`'s `LIDARR_URL`/`LIDARR_API_KEY` seed the Lidarr source once, then Settings owns them (a removed source isn't recreated). One Lidarr at most. Without it, requests and Discover are hidden and `/api/requests` answers 409. |
| 2026-10-30 | Folder sources: tags read with music-metadata, cached per file by size + mtime; untagged files fall back to "Artist/Album/NN Title" and join existing artists, albums and songs by name. Catalog rows keep the most trusted metadata (`meta_rank`). Untagged songs get `local:<hash>` ids until matched. Local folders are limited to `FOLDER_ROOTS` (Docker: `/host`, one broad read-only mount). |
| 2026-10-30 | Matching: a match is an overlay on a file's tags (`folder_matches`), so matched and tagged files share one mapping. MusicBrainz release search first, then Chromaprint/AcoustID, else unmatched; doubtful matches go to review; manual and ignored decisions stick. When a song's id moves from `local:` to a MusicBrainz recording, its favorites, playlist items, sound analysis and plays follow it. Matching shares MusicBrainz's 1 request/s queue with Discover ([matching and organize](server/matching-and-organize.md)). |
| 2026-10-30 | Remote folder sources over SSH (GNU find listings, stat/cat/tail over one connection, ffmpeg and fpcalc run remotely) or SFTP (no analysis or fingerprints). Remote tags come from byte ranges. Remote passwords are write-only secrets; `FOLDER_ROOTS` applies to local folders only; organizing stays local-only. |
| 2026-10-30 | SMB shares through rclone, not a Node client (the Node SMB libraries negotiate only SMB 2.0.2/2.1 without signing, which Windows 11 24H2 and Server 2025 require). One `rclone serve http` per share on 127.0.0.1 with random credentials; connection settings only through `RCLONE_SMB_*` environment variables with the password obscured. rclone is optional. NFS: mount it on the host and use a local folder. |
| 2026-10-30 | Organizing files: opt-in per folder source, review then apply. Layout `Artist/Album/NN Title.ext`, renames within the folder only, never overwrite, companions follow, every move journaled and undoable per batch. The server computes targets; the client only picks which files. |
| 2026-10-30 | Settings panels: Playback and Appearance are per device (stored in the browser); Sources, Requests, Analysis, Updates and the mix settings are server-wide (each account keeps its own ListenBrainz link and history). Turning requests off hides Request buttons and the server refuses new ones. |

## Deployment and updates

| Date | Decision |
|---|---|
| 2026-10-30 | Remote access through router port forwarding (static IP → NAS:4000) instead of Tailscale. Exposed without a login at first (the owner's call, with the risks spelled out); accounts since 2026-11-03; HTTPS through a reverse proxy is still open ([open items](plans/open-items.md)). |
| 2026-10-30 | NAS deployment as its own compose stack in `/volume1/docker/playarr`, not part of the media stack, so deploys never touch Lidarr and friends. Built on the NAS from the repo (no registry, no cross-building from an arm64 Mac). Docker needs sudo for the deploying user; the deploy uses it rather than adding them to the `docker` group ([updates and deploy](server/updates-and-deploy.md)). |
| 2026-10-30 | Automatic updates through a second compose service, `updater`, the only container with the Docker socket: giving it to Playarr would hand root on the host to a web app. Playarr and the updater talk only through files in `update/` (settings, a request flag, status with a heartbeat, the last log). Settings can't choose the branch, commit or repository (GitHub serves fork commits through the parent's API, so a free-form ref would let anyone deploy a fork): only `main` of `PLAYARR_REPO`. The updater recreates `playarr`, then a one-off container recreates the updater itself. |

## Listening, mixes and DJ transitions

| Date | Decision |
|---|---|
| 2026-11-01 | Song measurement runs in worker threads, one song at a time: on the NAS it blocked the main thread for seconds per song. |
| 2026-11-01 | Security before accounts existed: local-only actions need a home address, no proxy in between, and the server addressed by IP or a local name (`LOCAL_HOSTNAMES` for others), against DNS rebinding; every change request carries Playarr's own header (no cross-site requests); a saved Lidarr API key is only sent to the server it was saved for ([accounts and access](server/accounts-and-access.md)). |
| 2026-11-01 | Listening history and **Made for you**: 12 mixes made on the server in the background on a timer, in one household time zone, stored by recording id so matching doesn't empty them. Plays go to ListenBrainz (open data, the same ids end to end) rather than Last.fm. Mix covers are drawn in the client from the mix's album art and a hue per kind of mix, which is cheap on a NAS ([mixes](mixes.md)). *Profiles per device were superseded by accounts on 2026-11-03.* |
| 2026-11-01 | Gapless playback and crossfade with two `<audio>` elements taking turns: iOS keeps them playing in the background. Phones that fix the volume in hardware get gapless playback but no fades. |
| 2026-11-01 | **DJ transitions rendered by the server**, not mixed live in the browser: a locked iPhone can't run Web Audio or start a file at an exact moment, so each transition is a file played between A and B, and the phone still shows two songs. The style is picked automatically per pair, with a per-queue override (Auto, Party, No mixing). A pure, deterministic planner in `packages/mix` is shared by server and browser; desktop browsers also mix skips live ([mixing](mixing.md)). |
| 2026-11-02 | Beats and bars from Beat This! (small, MIT) in onnxruntime-web on the server, not the onset comb alone: the comb confused kicks with off-beats and found bars right about half the time. The model fixes phase, octave and bars; the comb keeps 0.01 BPM precision. WebAssembly rather than onnxruntime-node, so the Alpine image stays. |
| 2026-11-02 | Testing on iPhone Safari through the iOS Simulator: `pnpm sim` (`scripts/ios-sim/`) talks to the simulator's Web Inspector socket directly, so it needs nothing but Xcode (no `safaridriver --enable`, no Appium). It confirmed that over plain HTTP iOS Safari has no service worker, so offline songs on phones need HTTPS. |
| 2026-11-02 | **Even volume through levelled streams**: the server serves each song as a WAV at its level (`/stream/:id/levelled.wav?gain=`), turned up as well as down, because iPhones ignore an element's volume. Loudness is Playarr's own EBU R128 measurement (−14 LUFS target), not ReplayGain tags, so every song gets one. Transitions are rendered at the same levels. Cost: uncompressed audio over the network until there's transcoding ([streaming and art](server/streaming-and-art.md)). |
| 2026-11-02 | One tempo for everything: beat analysis's (the mix map), so covers, mixes and DJ mix never disagree. Settings → Analysis shows four analyses that don't overlap (beat, sound, loudness, tags). |
| 2026-11-02 | Joins between files are lined up on the sound itself on desktop browsers (cross-correlation through a Web Audio graph). Web Audio is kept to desktop browsers: iOS suspends it when the screen locks, which silenced the players. Elsewhere files take over in step by their reported times. |

## Accounts and the iOS app

| Date | Decision |
|---|---|
| 2026-11-03 | **Native iOS app** in SwiftUI with its own audio engine (AVAudioEngine), chosen over a web wrapper (App Review's minimum-functionality rule, and playback would still need a native engine) and over a hybrid with web views. iPhone and iPad, iOS 26 and later; CarPlay and Mac later. No third-party code in the app. The web stays a full client on phones ([iOS](ios/README.md)). |
| 2026-11-03 | The app keeps a list of servers, each with its signed-in accounts; downloads and caches are per server and account. Servers on the home network are found by Bonjour; elsewhere each is reached over HTTPS on its own domain, plain HTTP only for local addresses. |
| 2026-11-03 | The Xcode project is generated by XcodeGen from `apps/ios/project.yml` and not committed; XcodeGen is pinned and checksummed in `apps/ios/.tools/` (Homebrew isn't writable here). Swift models are generated from the shared TypeScript types, and contract tests decode real server responses. |
| 2026-11-03 | Signing and uploads only through the App Store Connect API key: no Apple ID, no fastlane. The archive is unsigned, `xcodebuild -exportArchive` signs it with the cloud-managed distribution certificate, and `altool` uploads it, so TestFlight needs no registered device and no certificate in a keychain. Build number = commit count. GitHub Actions on `macos-26` uploads pushes to main that change `apps/ios` ([iOS release](ios/release.md)). |
| 2026-11-03 | **Accounts replace profiles**: same ids, so history, mixes and ListenBrainz stay put; scrypt passwords, 256-bit session tokens stored as SHA-256 (Bearer for the app, an HttpOnly cookie the web switches between accounts), one-time setup codes so admins never choose passwords, in-memory sign-in rate limits per client address. Setup mode (no password yet) keeps an install working as before until the owner claims it from the home network. Admins replace the home-network rule. Library access per account is a view of the catalog built from only its sources. Favorites per account; playlists private unless shared. `GET /api/server` (stable UUID) and Bonjour `_playarr._tcp`. A forgotten owner password is reset on the server host (`cli.js reset-password`), never over the network. |
| 2026-11-03 | Requests are the same in every iOS build, gated by the server's switch and the account's right. App Review gets a reviewer account on the owner's server that sees only a Creative Commons folder, with no requests and no admin rights. |
| 2026-11-03 | The App Store listing lives in the repo (`apps/ios/store/`: one text file per field, settings in `app.json`); review contacts and the demo account come from the environment because the repo is public. Store screenshots are taken by a UI test against a local copy of the server with Creative Commons albums, not against a live server or a stub, so they're reproducible and show what App Review will see. The rest of the launch decisions are in the [App Store plan](plans/2026-11-03-ios-phase11-app-store.md). |
| 2026-11-04 | On the iPad the layout follows the web's breakpoint, not the device: the sidebar layout needs a regular-width window at least 768 points wide; narrower windows get the phone's tabs with the same page open. Keyboard shortcuts are menu commands; context menus mirror the ⋯ menus. Three App Intents, no extension; no Spotlight indexing, widgets or Live Activities (the system's Now Playing already covers them) ([layouts](ios/layouts.md)). |
| 2026-11-05 | Every iPhone screen turns sideways (at the owner's request), each with its own sideways style; sideways Now Playing opens like a gatefold sleeve, with the left thumb playing (cover, seek bar, transport) and the right thumb browsing (header and tracklist or lyrics). Turning the phone to open Now Playing is a setting, off by default since the pages turn too. |
